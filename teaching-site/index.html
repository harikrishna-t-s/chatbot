02 — The big picture

What exactly did we build?

Forget code for a second. In plain English: you built a webpage where you can type a question, and a few moments later, an answer appears — written by an artificial intelligence model running on a computer somewhere else in the world.

A webpage

The part you see and touch. A dark chat window, a text box, a "Send" button. This is what we call the frontend.

A little Python program

Running quietly in the background, waiting for messages, and forwarding them to the AI. This is the backend.

A borrowed brain

You didn't build the AI itself — nobody builds that alone. You borrowed one from Hugging Face, a company that hosts AI models for anyone to use.

Here's the honest version: almost no modern software is built entirely from scratch. Real engineers connect existing pieces — a database someone else wrote, a payment system someone else built, an AI model someone else trained — and write the "glue" code that makes them work together. That's exactly what you did today. That's not cheating. That is the job.

03 — Demystifying the magic

How does a chatbot "think"?

It doesn't. Not the way you do. The honest, unglamorous truth is that a chatbot is a very, very good autocomplete.

You've seen autocomplete before — when you're texting and your phone guesses the next word. Type "I'll see you" and it suggests "tomorrow" or "later." It's not reading your mind. It has simply seen millions of sentences before, and it knows which words tend to follow which other words.

A chatbot's AI model — called a large language model, or LLM — does the same thing, just at a much larger scale. It has "read" an enormous amount of text from the internet — books, articles, conversations, code — and learned the statistical patterns of language: which word is likely to come next, given everything written so far.

When you type a message into your chatbot, the model doesn't "look up" an answer in a database. It generates a reply one word at a time, each time asking itself: "given everything typed so far, what's the most likely next word?" It does this so fast and so well that the result reads like a thoughtful answer — even though under the hood, it's prediction, not understanding in the human sense.

Why this matters: this is exactly why AI models sometimes state confident-sounding nonsense — a phenomenon engineers call a "hallucination." The model isn't lying on purpose. It's predicting plausible-sounding text, and plausible isn't always true. Good developers treat AI answers as a helpful draft, not gospel.

04 — The absolute basics

Before we go further: what even is a computer?

You've used computers your whole life. But let's slow down and name what's actually happening, because everything else on this page builds on these ideas.

Hardware

The physical parts of a computer you could actually drop on your foot: the screen, the keyboard, the chip inside that does the calculating (the processor), and the storage that holds your files.

Software

Instructions that tell the hardware what to do. Software has no physical form — it's information. Your chatbot is software. So is every app on your phone.

Code

The actual text a person writes to create software — instructions written in a language a computer can follow, like app.py. Code is to software what a recipe is to a meal.

A program

A finished piece of software that does a specific job. Your chatbot is a program made of several smaller pieces working together.

Memory (RAM)

Short-term, working memory the computer uses while it's doing something — like your desk while you're working. Turn the computer off, and it's wiped clean.

Storage

Long-term memory — like a filing cabinet. Your app.py file stays saved on your hard drive even after you shut your laptop down.

A file

A named, saved chunk of information — text, an image, code. style.css is a file. It's a single, addressable thing you can open, edit, and save.

A folder

A container that groups related files together, so things don't turn into chaos. Your project has a static folder and a templates folder — each one holding files that belong together, the same way you'd keep your class notes in a labeled binder instead of one giant pile of paper.

Here's the part that trips people up: a computer's processor is, at its core, astonishingly simple. It doesn't "understand" Python or English. It only understands two things — on and off, represented as 1s and 0s. Everything you'll ever build — every website, every game, every chatbot — eventually gets translated down into unimaginably long strings of 1s and 0s that flip tiny switches on a chip billions of times per second.

You will never have to think in 1s and 0s. That's the whole point of programming languages like Python and JavaScript — they let humans write instructions in something closer to English, and a translator program converts it down to the 1s and 0s the processor actually runs.

05 — Building blocks of the web

How does a website actually work?

Every website you've ever visited — including the one you built today — is made of three layers, and they map perfectly onto building a house.

HTML

The structure

The walls, floors, and rooms. HTML says "here's a header, here's a text box, here's a button" — with no opinion about color or style yet. It's the skeleton.

CSS

The style

The paint, the furniture, the lighting. CSS decides that the background is black, the text is white, and the buttons have rounded corners. Same house, dressed up.

JavaScript

The behavior

The electricity and plumbing — the stuff that actually does something. JavaScript is what notices you clicked "Send" and reacts to it.

In your project, these three layers live in exactly the files you'd expect: templates/index.html is the structure, static/style.css is the style, and static/script.js is the behavior. Your browser (Chrome, Safari, Firefox — whichever you used) reads all three and paints the result on your screen.

Try it: right-click anywhere on almost any website and choose "Inspect" (or "View Page Source"). You're looking at the exact same kind of HTML and CSS that makes up your chatbot — just written by a bigger team. There is no secret extra layer. This is genuinely how the entire web is built.

06 — The part you can touch

Frontend: everything that happens in the browser

"Frontend" just means: whatever runs on your device, inside your browser. Let's name the pieces you actually interacted with.

The DOM

When your browser reads your HTML file, it builds a live model of the page in memory — a tree of every element (every button, every div, every paragraph). That live model is called the DOM (Document Object Model). JavaScript's whole job is to reach into that tree and change it — add a new message bubble, clear the input box, and so on.

Events

An event is something that happens that the page can react to: a click, a key press, a page load. In script.js, this line is listening for exactly one event: sendButton.addEventListener("click", sendMessage). Translation: "when this button is clicked, run the sendMessage function."

Rendering

The process of your browser turning HTML + CSS into actual pixels on the screen. Every time JavaScript adds a new chat bubble to the DOM, the browser instantly re-renders to show it — that's why your messages appear the moment you send them.

User interaction

Buttons, text boxes, and links exist so a human can tell the program what to do. Your <input id="user-input"> is a text box that holds whatever the student types until JavaScript reads it and does something with it.

💡 Your Debugging Superpower: Browser DevTools

If you press F12 (or right-click anywhere and select "Inspect"), your browser opens its Developer Tools. This is your command center as a web developer. It has two essential tabs:

  • The Console Tab: Shows any JavaScript error messages. If your script crashes, a red error message will appear here telling you exactly what line failed.
  • The Network Tab: Shows every request your browser makes to the internet, including the POST /chat request. You can click on it to see the exact message you sent and the JSON response returned by Flask.

Everything above happens entirely on your own laptop. No internet connection is required just to type in the box and see it appear — the browser is doing all of that locally. The internet only gets involved the moment we need to talk to something outside your machine, which brings us to the backend.

07 — The part behind the curtain

Backend: the program nobody sees

The backend is code that doesn't run in your browser — it runs somewhere else (in your case, on your own laptop, but pretending to be a distant "server"), quietly waiting to be asked for something.

Server

Any computer whose job is to wait for requests and respond to them. When you ran python app.py, your own laptop became a tiny server for as long as that program kept running.

Flask

A lightweight Python framework — a toolkit that handles the boring, repetitive parts of being a server (listening for connections, parsing requests) so you can focus on the interesting part: what to do with each request.

A route

An address on your server that does a specific job — like a room number. Your project has two: / (give me the webpage) and /chat (give me an AI reply for this message).

Request

A message asking the server to do something. When your browser loads the page, it's making a request. When JavaScript sends your chat message, that's also a request.

Response

Whatever the server sends back after handling a request — the webpage itself, or, for /chat, the AI's reply.

JSON

A simple, universal way of formatting data as text so any program in any language can read it — basically a structured list of labeled values, like {"message": "hello"}. It's the shared language your frontend and backend use to pass information back and forth.

@app.route("/chat", methods=["POST"])
def chat():
    # This function runs every time the browser sends
    # a POST request to /chat — i.e. every time you hit Send.
    data = request.get_json()
    user_message = data["message"]
    reply_text = ask_huggingface(user_message)
    return jsonify({"reply": reply_text})

Notice how directly this reads: get the message, ask the AI, send the reply back. That's the entire job of the backend, in five lines.

08 — Bridging the two

How does the frontend actually talk to the backend?

Through a JavaScript function called fetch(). Think of it as JavaScript picking up a telephone, dialing your Flask server, saying something, and waiting for a reply.

One request, animated

Browser
POST /chat
Flask server 
const response = await fetch("/chat", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ message: message }),
});

const data = await response.json();
// data.reply now holds the AI's answer

Notice the word await. Talking to a server takes time — maybe a fraction of a second, maybe a few seconds if the AI is thinking. await tells JavaScript "pause this function here and wait for the answer before continuing," without freezing the entire page. That's also exactly why you see a typing indicator (three bouncing dots) while you wait — it's the frontend being honest with you that a request is still in flight.

09 — The universal connector

What is an API, really?

API stands for Application Programming Interface — a phrase that explains nothing on its own. So: a restaurant analogy.

You

sit at the table and tell the waiter what you want: "I'll have the pasta."

Waiter

doesn't cook anything. They carry your order to the kitchen in a format the kitchen understands, and later carry the finished plate back to you.

Kitchen

does the actual work, completely out of your sight. You never need to know how the sauce is made.

An API is the waiter. It's a defined, agreed-upon way for one piece of software to ask another piece of software to do something, without needing to know how that something actually happens internally. Your Flask backend is a "customer" of the Hugging Face API: it sends a tidy, well-formatted request ("please generate a reply to this message"), and Hugging Face's servers do the actual AI work, then hand back a plate — a JSON response — with the answer on it.

This is why APIs are everywhere in software. Nobody wants to rebuild a weather forecasting system just to show today's temperature in an app — they call a weather API. You didn't want to train your own AI model from scratch — so you called Hugging Face's API instead.

10 — Meet the kitchen

What is Hugging Face?

Hugging Face is a company (and community) that hosts thousands of AI models on powerful computers, and lets developers like you call those models over the internet instead of needing your own supercomputer.

AI models

Pre-trained "brains" that already know how to do something — generate text, translate languages, describe images. Someone else spent enormous time and computing power training them, so you don't have to.

Hosting

Hugging Face keeps these models running on their own servers around the clock, so they're always available the moment you need them — the same way a restaurant keeps its kitchen staffed and ready.

Inference

The technical word for "actually using a trained model to produce an answer" — as opposed to training it in the first place. Every time your chatbot gets a reply, that's one "inference."

API keys

A private password-like string that identifies you to Hugging Face — proving the request is coming from your account, so they know who's using their servers (and can stop strangers from using yours for free).

Why an API key matters: your .env file holds your personal key. It's listed in .gitignore on purpose, so it's never accidentally shared or uploaded anywhere public. Treat an API key like a house key — anyone who has it can act as you.

Why does an entire industry build around APIs like this instead of everyone training their own models? Because training a large AI model can cost millions of dollars and requires warehouses of specialized computers. Hugging Face already did that work — renting a small slice of it through an API, often for free at small scale, is dramatically more realistic for a student project (or most companies, honestly).

11 — Inside the black box

The AI model: a few words you'll keep hearing

You don't need math to understand these — you already met the core idea back in "How does a chatbot think." Here's the vocabulary that goes with it.

The AI model itself — "large" because it was trained on a huge amount of text, and has a huge number of internal adjustable values (called parameters) that shape its predictions. The model your project talks to (configured in .env as MODEL_NAME) is one specific LLM.

Before predicting text, the model chops it into small chunks called tokens — often close to whole words, sometimes word-pieces ("un", "believ", "able"). It predicts one token at a time, not one full sentence at once. In app.py, max_new_tokens: 200 caps how many of these chunks the reply is allowed to contain.

The text you send the model — its starting point for prediction. In our project, the prompt is simply whatever you typed into the chat box.

The text the model generates after your prompt, token by token, until it decides it's finished or hits the token limit.

A dial from 0 to 1 controlling how "safe" versus "adventurous" the model's word choices are. Low temperature (near 0) picks the single most likely next word almost every time — repetitive but predictable. Higher temperature (our project uses 0.7) allows more surprising, varied word choices — more creative, occasionally less focused.

Everything the model can "see" at once while predicting — your prompt, and earlier messages in the conversation. Our chatbot is equipped with session-based memory, sending the last few exchanges as a structured history list so the AI remembers context between turns (which you can clear at any time using the "Clear" button).

12 — Coming home

Our project, file by file

Everything above was theory. Now let's point directly at the project on your laptop and name what every single file is doing there.

templates/

A folder Flask looks in automatically for HTML pages. Keeping it separate from your Python code is a convention that keeps projects organized as they grow.

index.html

The structure of your chat page: the header, the scrolling chat history, the typing indicator, the input box, and the Send button. Flask sends this file to your browser when you visit the site.

static/

Another folder Flask automatically knows about — for files that don't change per request: stylesheets, scripts, images. "Static" as in "doesn't change."

style.css

Every visual decision: the black background, the white rounded message bubbles, the bouncing typing-indicator dots, and the responsive rules that make the layout adapt to a phone screen.

script.js

The brain of the frontend: reads what you typed, displays your message, disables the button while waiting, calls fetch() to talk to Flask, and displays the reply (or a friendly error) when it comes back.

app.py

The entire backend. Defines the / route (serves the page), the /chat route (which manages session memory and calls the AI), and the /clear route (resets the AI's memory). It also performs startup environmental checks.

requirements.txt

A plain list of the external Python packages your project depends on — Flask, python-dotenv, and requests. Running pip install -r requirements.txt tells Python "go download exactly these tools before we start."

.env

Your private configuration file — holding your real HF_API_KEY and which MODEL_NAME to use. Kept out of version control on purpose, because it's personal and secret.

.env.example

A public, safe template showing what should go in .env — without any real secrets — so anyone setting up the project knows exactly which variables to fill in.

.gitignore

A list of files and folders that should never be uploaded to GitHub — like .env (your secret key) and venv/ (your local virtual environment, which is huge and machine-specific).

README.md

The instruction manual for the whole project — what it does, how to install it, how to run it, and how to troubleshoot it. Every well-made project has one of these.

14 — About that AI assistant you used

What is "vibe coding"?

There's a decent chance an AI assistant (maybe Claude) helped generate some of the code in this workshop. "Vibe coding" is the informal term for describing what you want in plain English and letting an AI write the code — steering by feel rather than typing every character yourself.

What it's genuinely good for

  • Skipping repetitive boilerplate, so you can focus on the interesting parts of a project
  • Getting a working first draft fast, to learn by reading and experimenting
  • Explaining unfamiliar code line by line, on demand
  • Unsticking you when you're stuck, the way a patient tutor would

Where it can hurt you

  • Code you don't understand is code you can't fix when it breaks
  • AI can be confidently wrong — see "hallucination" above
  • Copy-pasting without reading skips the exact process that builds real skill
  • It can quietly introduce security or logic mistakes a beginner won't catch

Using AI responsibly, in practice

  • Always read the code an AI gives you before running it — line by line, out loud if it helps.
  • Ask "why did you write it this way?" — a good AI assistant (and a good teacher) will explain.
  • Treat the first answer as a draft, not a finish line.
  • Test what it gives you. Break it on purpose. See what happens.
  • The goal isn't to never use AI — it's to never let it think for you.

What makes a good prompt

Vague

"Make a chatbot"

Specific

"Build a Flask backend with a /chat POST route that forwards a JSON message to the Hugging Face Inference API and returns the reply as JSON, with error handling for a missing API key."

Notice the good prompt names the tech stack, the exact behavior, the data format, and the edge cases. That specificity is what turned a vague wish into today's working project.

15 — The unglamorous truth

How developers actually build software

Not in a straight line. Not by memorizing everything. Here's what the real, everyday process looks like — including for the engineers who built the tools you used today.

  1. Think before you type

    What exactly is this supposed to do? Write it in a sentence before writing a single line of code.

  2. Break the problem down

    "Build a chatbot" is overwhelming. "Make a text box," then "make a button," then "make the button add a message to the screen" is not.

  3. Google relentlessly

    Every developer, at every level, searches the internet constantly. Not knowing something by heart is normal. Knowing how to find the answer fast is the actual skill.

  4. Read the docs

    Official documentation (like Flask's or Hugging Face's) is often the most accurate, up-to-date source — more reliable than a random forum post from six years ago.

  5. Experiment

    Change one small thing. Run it. See what happens. Repeat. Most understanding comes from poking at real code, not reading about it passively.

  6. Expect mistakes

    Professional developers hit errors constantly — typos, wrong assumptions, broken logic. An error message is not a verdict on your intelligence. It's a clue.

  7. Debug

    The methodical process of finding why something broke: reading error messages carefully, checking one assumption at a time, adding print statements to see what's actually happening.

  8. Iterate

    Ship something rough. Improve it. Ship again. Your chatbot today is version one — not the final form, just a solid starting point.

The reassuring truth: feeling confused while coding isn't a sign you're bad at this — it's the normal, permanent texture of the job, for everyone, forever, at every skill level. The difference between a beginner and a senior engineer isn't that the confusion goes away. It's that the senior engineer has gotten fast at resolving it.

17 — Your roadmap

What's next?

You now understand your first full project end to end. Here's a realistic map of where curious beginners tend to go from here — no pressure to do all of it, or in this exact order.

1

Python, properly

Go deeper on the language itself — loops, functions, data structures — beyond what today's project needed.

2

Git & GitHub

The standard way developers save versions of their code and collaborate. Think of it as "track changes" for entire projects.

3

JavaScript, in depth

You've seen the basics. Next: more advanced DOM manipulation, async patterns, and modern JavaScript features.

4

Databases

Right now your chatbot forgets everything after you close it. Databases (like SQLite or PostgreSQL) are how software remembers things long-term.

5

React

A popular frontend tool for building larger, more complex interfaces than plain JavaScript comfortably handles.

6

Machine learning

Go from using AI models to understanding how they're actually trained in the first place.

7

Cybersecurity

Now that you've handled an API key, learn how to protect systems and data more broadly.

8

The cloud

Learn how to put your Flask app on a real server on the internet, so anyone — not just you — can use it.
